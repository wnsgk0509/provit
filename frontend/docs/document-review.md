# AI원클릭첨삭 프론트 구조

## 진입

- 헤더와 마이페이지 **취업 문서 관리**의 메뉴 이름은 **AI원클릭첨삭**이다.
- `/document-review`는 로그인 후 이용한다.
- 마이페이지 오른쪽 **면접·첨삭 기록** 박스의 라디오에서 첨삭 기록을 선택하면 저장 내역을 조회한다. 20개씩 조회하고 박스 안의 **첨삭 기록 더 불러오기**로 이어서 확인한다. 목록은 박스 높이를 유지하며 내부에서 스크롤되고, 기록을 클릭하면 `/document-review?reviewNum=기록번호`로 이동한다. 기본값인 면접 기록은 기존 상세 모달과 성장 그래프의 면접 데이터를 재사용한다.
- 모의면접처럼 왼쪽에는 작은 진행 목차를 두고, 오른쪽의 하나의 큰 작업 박스에서 `서류 선택 → 첨삭 기준 설정 → 결과 확인` 컴포넌트를 전환한다. 모바일에서는 목차를 작업 박스 위에 배치한다.
- 하나의 서류 선택 박스 안에서 `이력서 → 자기소개서 → 포트폴리오(생략 가능) → 서류 선택 완료` 순서로 진행한다. 현재 단계의 선택 컴포넌트만 표시한다.
- `?resumeNum=12&letterNum=34&portfolioNum=56`으로 각 문서를 미리 선택할 수 있다. 실제 문서 목록에 존재하는 번호만 사용한다.
- 이전 `?type=cover-letter&document=34` 링크도 해당 문서 하나를 미리 선택하며, 이후 선택하면 새 쿼리 형식으로 전환한다.

## 통합 첨삭 흐름

1. 이력서 1개를 선택하고 원문 조회가 끝나면 자기소개서 단계로 이동한다.
2. 자기소개서 1개를 선택한 뒤 포트폴리오 단계로 이동한다. 포트폴리오 PDF는 1개를 추가하거나 생략한다.
3. 서류 선택 완료 화면에서 문서 목록을 확인한 뒤 **다음: 첨삭 기준 설정**으로 이동한다. 같은 작업 박스에서 전체 서류에 적용할 첨삭 기준과 추가 요청을 설정한다.
4. 선택한 서류 묶음을 하나의 요청으로 전달한다. 서류 간 일관성 검토는 기본으로 포함한다.
5. 요청을 시작하면 같은 작업 박스가 결과 단계로 전환된다. 결과는 종합 피드백, 전체 강점, 서류 간 일관성, 문서별 첨삭으로 구성한다. 오류 시 첨삭 기준으로 돌아가 다시 요청할 수 있다.

각 문서의 목록·상세 로딩, 오류·재시도, 빈 목록을 독립적으로 처리한다. 필수 문서의 원문을 모두 읽어야 요청할 수 있다. 선택한 포트폴리오의 조회가 실패하거나 진행 중이면 요청하지 않으며, 다시 선택하거나 선택을 해제해야 한다. 선택하지 않은 포트폴리오 목록 조회 실패는 필수 문서만 사용하는 요청을 막지 않는다.

왼쪽 목차, 이전 단계와 완료 화면의 변경 버튼으로 돌아가도 다른 종류의 선택과 첨삭 기준, 추가 요청은 유지한다. 문서를 변경하려면 서류 선택을 다시 완료해야 첨삭 기준 설정 단계와 요청 버튼을 사용할 수 있다. 포트폴리오 생략 시 기존 포트폴리오 선택을 해제한다. 이전 문서의 조회 응답이나 첨삭 결과가 변경된 서류에 표시되지 않도록 요청 대상을 구분한다. 원문은 변경하지 않으며 브라우저 저장소에 서류 내용이나 결과를 저장하지 않는다.

첨삭 기준은 select에서 **전체 종합 첨삭**, **문장 표현·가독성 중심**, **서류 간 일관성 중심**, **직무 적합성 중심**, **성과·구체성 중심**, **직접 입력** 중 하나를 선택한다. 기본값은 전체 종합 첨삭이고 선택한 기준의 설명을 표시한다. 직접 입력을 선택하면 필수 입력란과 글자 수를 표시하며 최대 200자까지 입력할 수 있다. 빈 값이나 공백만 있는 값은 요청할 수 없다. 다른 기준으로 바꿔도 직접 입력한 내용은 유지하되, 직접 입력을 선택했을 때만 요청에 포함한다. 추가 요청은 별도 선택 입력이며 최대 200자다.

## 독립 서비스 경계

`src/api/documentReviewApi.js`는 모의면접과 분리된 첨삭 서비스 경계다. 공통 문서 조회 API를 사용하지만 모의면접 API·세션·점검시간 게이트를 사용하지 않는다.

백엔드 더미 저장 API를 연결하고 이전 서비스 준비 중 분기를 제거했다. **더미 첨삭 결과 저장하기** 버튼은 공통 axios 클라이언트로 `POST /api/document-reviews`를 호출한다. 선택한 문서·기준·추가 요청 및 서버의 고정 예시 결과를 DB에 저장한다. AI는 호출하지 않으며 입력 기준과 추가 요청은 더미 피드백 내용에 반영되지 않는다. 저장된 결과에는 `resultSource = 'DUMMY'`와 기록 번호가 있으며 화면에서 더미 안내를 표시한다.

왼쪽 목차의 **결과 예시 보기**는 기존 정적 미리보기다. 이 버튼은 API 호출이나 DB 저장을 하지 않는다. 포트폴리오를 선택하고 조회한 경우에만 포트폴리오 관련 미리보기를 표시한다.

저장 완료 후 `?reviewNum=기록번호`로 이동해 상세 API를 조회한다. 새로고침하거나 페이지 하단의 **저장된 첨삭 기록**에서 과거 결과를 선택해 다시 확인할 수 있다. 기록은 20개씩 최신순으로 조회하며 이전/다음 페이지와 새로고침을 제공한다. 상세 화면에는 저장 시각, 선택 문서의 제목/파일명, 첨삭 기준, 직접 입력 기준 및 추가 요청을 함께 표시한다. 원본 문서의 현재 존재 여부와 독립적으로 결과를 조회한다.

저장 요청의 제한 시간은 30초다. 아래 계약은 구현된 서버 API이며 응답은 공통 `ApiResponse.data`에서 꺼낸다. AI 호출은 향후 별도로 연결한다.

요청:

```json
{
    "resumeNum": 12,
    "letterNum": 34,
    "portfolioNum": null,
    "reviewMode": "comprehensive",
    "customCriteria": null,
    "instructions": "각 서류에 적은 프로젝트 역할과 성과가 일관되는지 확인해 주세요."
}
```

`resumeNum`과 `letterNum`은 필수이며, 포트폴리오를 선택하지 않으면 `portfolioNum`은 `null`이다. 기존 단일 문서 요청의 `documentType`, `documentNum`은 사용하지 않는다.

응답의 `data`:

```json
{
    "summary": "종합 피드백",
    "strengths": ["서류 전체에서 드러난 강점"],
    "documentReviews": {
        "resume": {
            "summary": "이력서 피드백",
            "strengths": ["이력서의 강점"],
            "improvements": [
                {
                    "section": "경력 1",
                    "title": "개선 방향",
                    "issue": "문제점",
                    "original": "검토한 원문",
                    "suggestion": "수정 제안문",
                    "reason": "수정 이유"
                }
            ]
        },
        "coverLetter": {
            "summary": "자기소개서 피드백",
            "strengths": [],
            "improvements": []
        },
        "portfolio": null
    },
    "consistencyIssues": [
        {
            "type": "mismatch",
            "title": "경력 기간 확인",
            "sources": [
                { "documentType": "resume", "section": "경력 1", "text": "비교 근거" },
                { "documentType": "cover-letter", "section": "문제 해결 경험", "text": "비교 근거" }
            ],
            "recommendation": "사용자에게 확인하거나 개선할 내용"
        }
    ]
}
```

문서별 결과는 `summary`, `strengths`, `improvements`의 같은 구조를 사용한다. 포트폴리오를 선택하지 않으면 해당 결과는 `null`이고 일관성 근거에도 포트폴리오가 포함되지 않아야 한다. 일관성 항목은 `mismatch`(내용 불일치), `missingEvidence`(근거 보완), `needsConfirmation`(확인 필요)로 구분한다. 포트폴리오 근거에는 페이지 정보를 포함할 수 있다. 비교 항목이 없으면 `consistencyIssues`는 빈 배열이다.

`reviewMode`는 `comprehensive`, `expression`, `consistency`, `jobFit`, `evidence`, `custom` 중 하나다. 기존 체크박스의 `focusAreas` 배열은 사용하지 않는다. 직접 입력 시 `customCriteria`는 앞뒤 공백을 제거한 필수 문자열이며 최대 200자다. 다른 기준이면 `customCriteria`는 `null`이다. 추가 요청은 200자 이하다. 프론트와 서버 모두 입력을 검증하고 서버는 기존 문서 조회 서비스로 소유권을 확인한다. 전체 저장은 트랜잭션으로 처리하며 결과 자식 행 저장 실패 시 요청까지 롤백한다. 서버 구현과 테스트는 [저장 설계 문서](../../backend/docs/document-review-storage.md)를 참고한다.
