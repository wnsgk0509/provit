# 모의면접 OpenAI API 연결

## 설정

`src/main/resources/api.properties`의 `api.openai.key`에 실제 키를 설정하고 서버를 다시 실행한다.
실제 키는 저장소에 커밋하지 않는다. 키가 없으면 서버는 기동되지만 면접 시작 요청에서 설정 오류를 반환한다.

모델은 `gpt-6-sol`, reasoning effort는 `medium`으로 고정한다.
Java 17의 HTTP 클라이언트로 `https://api.openai.com/v1/responses`를 호출한다.
실제 생성기는 `OpenAiInterviewGenerator`이며 기존 `DummyInterviewGenerator`는 Spring Bean으로 등록하지 않는다.

## 호출과 프롬프트

모든 면접은 일대일로 고정한다. 화면·시작 요청·서버 DTO·AI 입력에서 면접 스타일 선택을 제거했으며, 시작에는 서류와 `interviewDifficulty`만 필수로 받는다. 공고와 포트폴리오는 선택 사항이다.

난이도별 질문 지침은 `difficulty-easy.txt`, `difficulty-normal.txt`, `difficulty-hard.txt`에서 관리하며 선택한 지침만 각 질문 생성 입력의 `difficultyGuide`로 보낸다. 난이도는 전체 5문항의 구성이나 질문 수를 바꾸지 않는다.

| 난이도 | 서류 질문 | 직무 지식 | 문제해결 | 꼬리질문 |
|---|---|---|---|---|
| EASY: 일반면접 | 역할·기본 행동 | 뜻·목적·기초 원리 | 단순한 상황의 첫 대응 | 모호한 내용을 쉬운 사례로 구체화 |
| NORMAL: 심층면접 | 선택 근거·기여 증거 | 작동 원리·적용 기준·차이 | 원인을 구분할 기준·해결 방법의 타당성 | 판단 근거·결과 검증·대안 비교 |
| HARD: 압박면접 | 주장의 입증·선택의 한계 | 반례·단점·성립하지 않는 조건 | 두 제약이 충돌할 때의 우선순위 | 실제 응답에 반론·추가 제약을 제시해 판단 검증 |

압박면접은 정중하고 직접적인 검증으로 진행하며 없는 모순·실패를 단정하거나 인신공격하지 않는다. 평가에는 난이도 코드와 실제 질문·응답을 사용하고 난이도 이름 자체로 점수를 가감하지 않는다. 프론트의 난이도 선택에는 위 차이를 설명하는 안내를 표시한다.

공고 목록의 모의면접 버튼은 선택한 공고를 React Router의 `state.recruitment`로 전달한다.
면접 시작 요청 `POST /api/interview/start`에는 기존 설정과 함께 선택 사항인 `recruitment` 객체를 보낸다:

```json
{
  "recruitmentNum": 42,
  "companyName": "테스트 기업",
  "title": "백엔드 개발자 채용",
  "jobName": "백엔드 개발,Java",
  "locationName": "서울",
  "experienceLevel": "신입"
}
```

공고 정보는 면접 세션에 보관하고 첫 질문, 4번 문제해결 질문, 5번 꼬리질문, 최종 평가의 모든 AI 입력에 `recruitment`로 전달한다. AI에는 공고 번호를 제외한 다섯 텍스트 필드만 보낸다. 공고의 모집 직무와 경력 조건을 우선 기준으로 사용하고 이력서의 분야는 지원 경험의 배경으로 유지한다. 회사의 기술 스택·인재상 등 공고에 없는 내용은 추정하지 않으며 근무지를 능력 평가 기준으로 삼지 않는다.
공고 없이 시작하면 기존 이력서 기반 면접으로 진행한다. 화면에 공고 요약을 표시하고 같은 공고로 다시 면접을 시작할 수 있다. 동일한 `requestId`로 공고 정보를 바꾸는 요청은 거부한다. 공고 정보는 현재 세션에만 보관하며 DB 구조는 변경하지 않는다.

프롬프트 파일: `src/main/resources/interview/prompts/`.
모든 단계는 `common.txt`에 해당 단계 파일을 덧붙여 instructions로 사용한다.
질문 생성 단계에는 `question-rules.txt`, 질문·답변을 보내는 단계에는 `answer-format.txt`를 추가한다.

총 5문항의 구성과 순서는 다음과 같다. 포트폴리오 유무는 이번 면접에서 포트폴리오를 선택했는지로 판단한다.

| 번호 | 포트폴리오 선택 | 포트폴리오 미선택 |
|---|---|---|
| 1 | 자기소개서 | 자기소개서 |
| 2 | 포트폴리오 | 자기소개서의 다른 소재 |
| 3 | 직무 관련 지식 | 직무 관련 지식 |
| 4 | 직무 관련 문제해결능력 | 직무 관련 문제해결능력 |
| 5 | 1~4번 응답 중 하나에 대한 꼬리질문 | 1~4번 응답 중 하나에 대한 꼬리질문 |

3번은 개념·원리의 이해도, 4번은 가상의 직무 문제 상황에서 판단 능력을 확인한다. 5번은 비어 있지 않은 응답 중 검증할 가치가 있는 하나를 선택하고 마지막 응답으로 고정하지 않는다. 모든 응답이 비어 있으면 앞선 핵심 질문 하나를 좁혀 묻는다.

| 단계 | 추가 프롬프트 | 입력 | 출력 토큰 상한 |
|---|---|---|---:|
| 시작: 1~3번 생성 | document.txt | 직무·설정·이력서·자기소개서·선택한 포트폴리오 PDF | 900 |
| 3번 답변 제출: 4번 문제해결 질문 생성 | follow-up-4.txt | 직무·설정·질문/답변 1~3 | 600 |
| 4번 답변 제출: 5번 꼬리질문 생성 | follow-up-5.txt | 직무·설정·질문/답변 1~4 | 600 |
| 5번 답변 제출 | evaluation.txt | 직무·설정·서류 원문·선택한 포트폴리오 PDF·질문/답변 1~5·이전 평가 요약 | 1400 |

출력 한도에는 추론 토큰이 포함된다. 미완성·거절·형식 오류·API 오류에는 자동 생성 재호출을 하지 않는다.
질문은 최대 120자, 평가 문구는 각 최대 250자로 JSON Schema와 서버에서 검증한다.
이력서·자기소개서·서류 제목을 포함한 documentText는 최대 9,000자이며 초과 시 첫 API 호출 전에 안내한다. 포트폴리오 PDF 본문은 이 글자 제한에 포함하지 않으며 내용을 임의로 잘라 질문을 생성하지 않는다.
4·5번 질문 생성에는 원문 서류를 보내지 않는다. 최종 평가에는 면접 시작 시점의 서류 원문과 선택한 포트폴리오 PDF를 보내 서류 일치성을 비교한다. 모든 단계에서 사용자 번호와 파일 경로를 보내지 않으며 `store=false`를 사용한다.

## 평가 항목과 저장 계약

| 평가 항목 | JSON 필드 | Oracle 컬럼 | 평가 기준 |
|---|---|---|---|
| 서류 일치성 | documentConsistencyScore | DOCUMENT_CONSISTENCY_SCORE | 제출 서류의 경험·경력·기술과 면접 답변의 일관성 |
| 전문성 | expertiseScore | EXPERTISE_SCORE | 지원 직무에 필요한 지식과 경험의 구체성 |
| 문제해결능력 | problemSolvingScore | PROBLEM_SOLVING_SCORE | 문제 상황 분석과 적절한 해결 방법 제시 |
| 논리력 | logicScore | LOGIC_SCORE | 주장·근거·결과의 연결과 명확한 답변 구조 |
| 의사소통능력 | communicationScore | COMMUNICATION_SCORE | 질문 의도 파악과 명확하고 간결한 핵심 전달 |

각 항목은 0~100점이고 종합 점수는 다섯 점수의 동일 가중치 평균을 소수점 첫째 자리까지 반올림한다. DTO, JSON Schema, MyBatis 저장·조회와 프론트의 결과·상세 기록·비교 그래프는 같은 필드를 사용한다. 이전 결과 요약도 위 다섯 필드로 보낸다.

평가 기준은 `evaluation.txt`에서 항목별로 독립 적용한다. 서류에 없는 추가 설명을 곧바로 모순으로 보지 않으며, 가상 상황의 답변을 실제 경력 주장으로 취급하지 않는다. 판독할 수 없는 포트폴리오 내용과 무응답에서는 평가 근거를 만들어내지 않는다.

`schema.sql`은 새 평가 컬럼을 포함한 신규 테이블 생성 스크립트다. 이미 만들어진 Oracle 테이블에는 파일 수정만으로 변경이 적용되지 않으므로 배포 전에 기존 데이터 보존·재평가 정책에 맞춰 스키마를 별도로 변경해야 한다. 이전 기준으로 산출된 점수를 새 항목 점수로 그대로 옮기지 않는다. 로컬 코드 작업에서는 실행 중인 DB를 변경하지 않는다.

## 포트폴리오 원본과 질문 반영

- 사용자가 선택하고 소유권이 확인된 포트폴리오는 PDF 원본을 Responses API의 `input_file`로 보낸다. `file_data`는 PDF 바이트의 Base64 데이터 URI이고 파일명은 `portfolio.pdf`, `detail`은 `high`다. 별도 Files API 업로드는 하지 않는다.
- PDF의 텍스트와 페이지 이미지를 모델이 함께 읽는다. PDFBox는 원본의 유효성만 확인하며 본문을 텍스트로 중복 전송하지 않는다. 이미지로만 된 PDF도 지원하고, 20MB 초과·읽을 수 없는 파일·페이지 없는 파일·암호화된 PDF는 생성 전에 거부한다.
- PDF는 최초 질문 생성과 최종 평가 요청에 첨부한다. 서류 수정·삭제 여부와 관계없이 같은 제출 자료를 비교하기 위해 시작 시점의 PDF 바이트를 진행 중인 세션에 보관한다. 평가 성공·실패 후 바이트를 해제하며, 초기·후속 질문 생성 실패 시에도 해제한다. 면접 종료·만료 시 세션과 함께 정리한다. 컨텍스트 JSON과 문자열 표현에는 PDF 바이트를 포함하지 않는다.
- `hasPortfolio=true`이면 2번 질문만 첨부 PDF의 구체적인 작업물에 직접 근거해야 하며 질문에 `포트폴리오`를 명시한다. 서버는 2번에만 이 단어가 있는지 검증하며, 누락·위치 오류·중복 시 면접을 시작하지 않고 오류를 반환한다. `hasPortfolio=false`일 때 이 단어가 포함된 질문도 거부한다. 단어 검증만으로 실제 근거의 정확성을 보장하지는 않으므로 실제 PDF로 질문 품질을 확인해야 한다.
- PDF가 없으면 `hasPortfolio=false`로 전달하고 첨부 자료를 가정하지 않도록 지시한다. 불명확한 수치·도표는 추정하지 않으며 PDF 안의 명령도 자료로만 취급한다.
- PDF 입력과 고해상도 페이지 이미지, 평가 단계의 원문 재전송으로 입력 토큰이 증가한다. 모델·추론 수준·4회 호출·출력 상한은 유지한다. 단계별 로그의 `inputTokens`와 `estimatedUSD`로 실제 증가분을 확인한다.

입력 형식 참고: https://developers.openai.com/api/docs/guides/file-inputs

## 토큰 절감 구조

- 질문 생성에는 선택한 난이도의 문항 유형별 지침만 `difficultyGuide`로 보낸다. 일대일 진행은 공통 프롬프트에서 고정한다. 평가에는 질문 작성 규칙을 보내지 않는다.
- 첫 응답은 질문 문자열 3개, 후속 응답은 `questionText`만 생성한다. 질문 번호·유형은 서버에서 채워 프론트와 저장에 사용하던 DTO 형식을 유지한다.
- 질문·답변 배열의 순서로 번호와 위 구성의 질문 유형을 표현한다. 기존 API의 `questionType` 값은 생성 단계 구분을 위해 1~3번 `DOCUMENT`, 4~5번 `FOLLOW_UP`을 유지하며, 화면에는 실제 문항 구성에 맞는 유형을 표시한다. 각 항목의 반복되는 번호·유형과 `timedOut=false`는 생략하며 `timedOut=true`는 전송한다.
- 서류·질문·답변 원문, 이전 평가 요약, 질문 검증 기준과 평가 기준은 보존한다. 모델·추론 수준·4회 호출·출력 상한은 그대로 유지한다.
- 원문 요약이나 잘라내기 없이 요청·응답의 반복 형식만 줄인다. 실제 출력 품질과 절감 토큰은 실제 면접 사용량으로 확인해야 한다.

## 오류와 중복 처리

프론트는 시작마다 UUID requestId를 생성하고 통신 실패 재시도에는 같은 번호를 사용한다.
같은 요청 번호의 시작은 서버 메모리에서 성공 또는 실패 결과를 재사용한다. 재시작·만료 이후에는 새 면접을 시작해야 한다.
1·2번 답변 제출은 추가 생성 요청 없이 이미 생성한 질문을 반환한다.
제출 재시도와 저장 실패 재시도는 기존 생성 결과를 재사용한다. 평가한 5번 답변은 수정할 수 없다.
생성 실패는 새 면접이 필요하고, 저장 실패는 같은 답변으로 다시 저장할 수 있다.
오류 응답의 data에는 message, restartRequired, answerLocked를 전달한다.
서버 요청 제한 시간은 120초, 프론트 면접 요청 제한 시간은 150초다.

## 이어가기와 점검 시간

- 진행 중인 질문·제출한 답변·면접 설정·공고 정보는 서버 힙 메모리에 보관한다. 브라우저 `localStorage`에는 사용자별 면접 번호, 현재 문항의 작성 중인 답변, 제출 잠금 여부와 만료 시각만 자동 저장한다. 진행 상태를 DB에 저장하지 않으며, 완료된 면접 결과는 기존대로 DB에 저장한다.
- `GET /api/interview/{historyNum}/session`으로 로그인한 본인의 서버 상태를 다시 조회한 뒤 `이전 면접 이어가기`를 제공한다. 이미 제출된 답변은 서버 상태를 따르고, 현재 문항의 초안만 브라우저에서 복원한다. 최종 평가 후 저장에 실패한 답변은 서버의 평가된 답변으로 복원하고 변경을 막는다. 복원 자체는 AI를 호출하지 않는다.
- `저장하고 나가기`나 새로고침·브라우저 종료 후 같은 브라우저에서 이어갈 수 있다. 답변 제한 시간 120초는 나간 동안에도 흐르며 이어가기 때 초기화하지 않는다. 서버 재시작이나 다른 서버 인스턴스로 연결되면 기존 세션을 이어갈 수 없다.
- `DELETE /api/interview/{historyNum}/session`으로 본인의 이전 면접을 종료하고 새 면접을 시작할 수 있다. 다른 사용자의 세션에는 접근할 수 없다.
- 한국시간(`Asia/Seoul`) 기준 시작한 날짜의 **23:55**에 모든 임시 세션과 시작 요청 캐시를 만료·정리한다. 기존 30분 미응답 만료는 제거한다. 정리 작업이 늦어지더라도 각 요청에서 고정된 만료 시각을 검사하므로 다음 날 이어갈 수 없다. 브라우저가 닫혀 있을 때는 다음 접근 시 만료된 초안을 삭제한다.
- 매일 **23:55 이상, 00:00 미만**에 모의면접 진입·시작·이어가기·답변 제출을 차단한다. `GET /api/interview/availability`는 인증 없이 점검 여부, 서버 시각과 다음 상태 변경 시각을 반환한다. 화면은 진입·포커스 복귀·주기적 확인과 서버가 알려준 23:55 시각에 점검 alert를 표시하고 홈으로 이동한다. 점검 시간의 면접 API는 HTTP 503과 `maintenance=true`를 반환한다. 기존 완료 기록 조회는 가능하다.
- 시작·제출·복원 응답의 `serverTime`, `questionDeadline`, `expiresAt`는 Unix epoch 밀리초다. 브라우저 타이머는 서버가 알려준 남은 시간으로 설정한다. 점검 전에 시작된 생성 요청도 완료 시 만료 여부를 다시 검사해 만료된 진행 상태를 되살리지 않는다.

## 비용과 검증 범위

단계별 로그에 입력·캐시 읽기·캐시 쓰기·출력·추론 토큰과 Standard 가격 기준 추정 USD를 남긴다.
계산 기준은 입력 $2/백만 토큰, 캐시 읽기 $0.20/백만 토큰, 캐시 쓰기 $2.50/백만 토큰, 출력 $10/백만 토큰이다.
캐시 읽기·쓰기는 입력에서 분리해서 계산하고 추론은 출력에 이미 포함되므로 중복 합산하지 않는다.
캐시 쓰기 정보가 없으면 `cacheWriteReported=false`이며 추정 비용은 캐시 쓰기 0을 가정한다. 추론 정보가 없으면 `reasoningTokens=unknown`으로 기록한다.
가격 참고: https://developers.openai.com/api/docs/models/gpt-6-sol
추론을 포함한 출력 상한 합계는 3,500토큰($0.035)이다. 총 $0.05 이하는 입력 사용량에 따라 달라지며 보장하지 않는다.
실제 키를 넣은 뒤 비용과 완성률을 확인해야 한다. 로컬 테스트는 모의 HTTP 서버만 사용한다. 질문 생성·평가에 동일한 서류와 PDF 원본 전송, 이미지 PDF 준비, 포트폴리오 질문 필수 검증, 평가 성공·실패 시 원본 해제, 4·5번 질문 생성의 PDF 미전송을 검증한다. 실제 모델의 이미지 해석 품질과 비용은 이 테스트로 확인하지 않는다.
새 평가 컬럼과 매퍼의 저장·조회, DTO 점수 필드 계약은 로컬 테스트로 검증한다. 실제 Oracle 스키마 변경과 DB 저장 길이 확인은 별도로 필요하다.
